# 편집기 성능 측정 (단계 E)

`EditorPaneWidget`(브레드크럼 + 거터 + 본문 + 검수 막대)을 헤드리스로 1200x800 프레임에 그려 측정한다.
"입력 지연"은 **키 이벤트 → 그 프레임이 다 그려질 때까지**(텍스트 편집, 모든 리스너, 캐럿 따라가기, 페인트 포함)이다.
OS의 이벤트 전달과 모니터 출력 지연은 포함하지 않는다.

## 실행

```bash
./gradlew :app:editorBenchmark                    # 1M, 10M 문자 모두 → app/build/reports/editor-perf.md
./gradlew :app:editorBenchmark -Pchars=1000000    # 크기 지정
./gradlew :app:test --tests '*EditorPerformanceTest'   # 회귀 기준 (1M)
```

## 측정 결과 (4 CPU, JDK 25, 2026-10-02)

| 항목 | 1,000,000자 (6,631줄) | 10,000,000자 (66,634줄) |
| --- | --- | --- |
| 로드(갭 버퍼 + 줄 인덱스) | 50 ms | 103 ms |
| 힙 사용량 | 7.1 MB | 42.3 MB |
| 스크롤 프레임 (무작위 점프) p50 / p95 / p99 | 1.99 / 4.16 / 5.12 ms | 2.06 / 2.92 / 3.31 ms |
| 제자리 입력 → 프레임 p50 / p95 / p99 | 1.72 / 3.44 / 7.01 ms | 1.39 / 2.03 / 3.62 ms |
| 캐럿 점프 후 입력 → 프레임 p50 / p95 / p99 | 2.06 / 3.33 / 3.62 ms | 3.28 / 4.53 / 4.92 ms |
| 실행 취소 → 프레임 p50 / p95 / p99 | 1.58 / 2.15 / 3.11 ms | 2.97 / 4.28 / 5.72 ms |
| 스크롤 프레임당 할당 | 70 KB | 70 KB |

문서가 10배 커져도 프레임 시간이 거의 늘지 않는다 = 화면에 보이는 줄만 처리한다는 뜻이다.
`EditorPerformanceTest`가 "한 프레임/한 키 입력이 문서 전체를 읽지 않는다"를 문자 읽기 횟수로 직접 검증한다.

알려진 관찰: 10M 문자에서 제자리 입력의 `max`가 한 번 약 200 ms까지 튀었다(첫 입력 시 캐럿을 문서 중간으로
옮기며 갭 버퍼의 갭이 수백만 자를 이동한 비용 + GC로 추정). p99는 영향받지 않았다. 실제 앱에서 거슬리면
갭 이동을 백그라운드로 미루는 방안을 검토한다.

## 회귀 기준 (`EditorPerformanceTest`, 1M자)

측정값의 약 10배 여유를 두어, 느린 CI 기계가 아니라 **문서 길이에 비례하는 작업이 끼어드는 회귀**만 잡는다.

| 항목 | 기준 |
| --- | --- |
| 스크롤 / 입력 / 실행 취소 프레임 p95 | ≤ 33 ms (30 fps) |
| 같은 항목 p99 | ≤ 100 ms |
| 스크롤 프레임당 할당 | ≤ 1 MB |
| 프레임 1회가 읽는 문자 수 | < 150,000 (1M 문서에서) |
| 키 입력 1회가 읽는 문자 수 | < 150,000 |

## 알려진 한계

- 한 줄이 수만 자를 넘는 문서(줄바꿈 없는 한 덩어리)는 줄 단위 그리기라 느려진다. 웹소설은 문단=한 줄이라 해당되지 않는다.
- repaint 면적(dirty area)은 아직 계측하지 않는다(헤드리스에서는 `RenderScheduler`를 쓰지 않음).
- 분할된 두 창이 같은 문서를 보면 캐럿·선택을 공유한다(`TextArea`가 캐럿을 갖고 있기 때문).
